# 调度流分层选点

Status: implemented

## Problem

flow 是一条线性管道：每个项求值自己的规则，命中就把节点追加进池，管道走完后一次性加权随机。管道没有"层"的概念，"某类客户端优先走某组节点"只能用大权重模拟，配置里因此出现成片的 `999`。

优先级因此是概率而不是保证。相对普通节点的个位数权重，`999` 只是把落到其它节点的概率压得很小，压不到零；而"没随到"时的行为无法预测，也无法在配置上表达"只有这层全挂了才允许往下"。

权重被迫承担两种语义。一部分权重是刻意的流量配比——CDN 与普通节点之间维持的比例，用来在流量成本与普通节点负载之间取平衡，普通节点跑起来比 CDN 便宜得多，比例配错任一方向都有真实代价。另一部分权重是伪优先级。两者混在同一个数字里，调一个必然动另一个，且从配置上分不出哪个是哪个。

跨层降级无法表达。`break` 只能表达"命中即停"（其条件性问题见[调度流的截断命令](2026-08-27-flow-control-commands.md)），而"本层节点全部不可用才降级"要求选点逻辑知道层的边界，管道级的中断做不到。

## Decision

`FlowItem` 增加 `tier` 序号，数字越小越优先，缺省 0。选点按层从最优先向下尝试：只有一层内所有节点都不可用（权重全零、健康检查失败、被 `banned`、被能力门剔除）时才降到下一层。层内的取舍仍是加权随机，权重因此回归单一语义——同层内的流量配比。

不写 `tier` 的配置全部落在同一层，行为与分层引入前一致。这让分层可以按资源逐个迁移。

**层信息不进池子。** 池条目的形状 `(名字, 权重)` 会原样序列化给 JavaScript 插件，插件返回的也是这个形状，改动它等于改插件 API。层归属放在一张以池条目名为键的旁挂表里，与既有的 `plugin_server_mapping` 同一模式。

**层在条目压入池子时记录，不靠前后对比。** 同一项内 `server` 后面紧跟 `poolize` 是合法写法，若等到项执行完再补记，那次 `poolize` 看到的条目就还没有层归属，会被当成最优先层。插件可以整体替换池子，因此插件产出的条目按"尚未归属"补记本项的层。

**同一节点被多层引用时按最优先的那层处理。** 否则层归属取决于配置的书写顺序，不可预测。

**选中的层随结果返回**，进入每请求的选点日志（`tier=`）。降级本身另有一条 warn：它意味着一整层当前没有可用节点，属于值得注意而非常态的事件。所有层都无可用节点时清空池子并由调用方报 `NO_RES_AVAILABLE`——池里若留着未解析的节点名，会被当成 URL 返回给客户端。

## Alternatives considered

**继续用大权重模拟优先级。** 落选：概率性而非保证，且强迫权重承担两种语义。加大到 `999999` 只是把概率压得更低，压不到零，而"没随到"时选中的正是本该避开的节点。

**只修 break 的条件判断，不引入分层。** 落选：`break` 只能表达"命中即停"。跨层降级要表达的是"本层节点全部不可用才往下"，这要求选点逻辑知道层的边界。

**用 priority 数字字段代替 tier。** 与 tier 等价，差别在命名。选 tier 是因为它直呼"层"，而 priority 容易与权重被读成同一维度上的两个数值。

**把层塞进池条目，变成 `(名字, 权重, 层)`。** 落选：池条目会原样序列化给插件，插件返回的也是同一形状，改动它是插件 API 的破坏性变更，而收益仅是省掉一张旁挂表。

**层信息在每项执行后按池子前后差分补记。** 落选：这样不必给项内部传层表，但同项内 `server` 后跟 `poolize` 会看不到本项的层；且插件替换整池时差分认不出哪些是新条目。

**降级时把上一层的节点也留在池中作为备选。** 落选：那就退回了概率模拟，分层的意义正是"上一层可用就绝不用下一层"。

## Verification

| 判据 | 结果 |
|---|---|
| 优先层可用时不降级 | PASS：`a_usable_top_tier_is_never_bypassed_by_a_heavier_lower_tier` 用权重 5 对 100 的两层跑 30 次，全部落在优先层 |
| 层内节点全部不可用时降到下一层 | PASS：`an_exhausted_tier_falls_through_to_the_next` |
| 所有层耗尽时报 `NO_RES_AVAILABLE` | PASS：`all_tiers_exhausted_reports_no_resource`，同时确认不会把节点名当 URL 返回 |
| 不写 tier 的配置落在同一层 | PASS：`items_without_tiers_compete_in_one_tier` 跑 80 次，分开书写的两个等权节点都出现过 |
| 同层内权重仍表达流量配比 | PASS：`weights_within_a_tier_still_split_traffic` 断言同项节点同层且权重原样保留 |
| 同一节点被多层引用取最优先层 | PASS：`a_server_referenced_by_several_tiers_takes_the_highest`（按 3、1、4 顺序引用后归属为 1） |
| 日志能看出本次选点来自哪个层 | PASS：每请求的选点日志含 `tier=`；降级另有 warn 指明是哪一层耗尽 |
| 插件产出的节点继承所在层 | 未覆盖：补记逻辑已实现，但没有插件参与的自动化测试 |
| 配置中不再有仅表达优先级的 `999` 类权重 | 未做：配置不在本仓库内，迁移在部署侧进行 |
| `dfs2 validate` 报出引用未定义节点的 flow | PASS：见[未定义节点引用的校验与摘除](2026-08-27-undefined-flow-server-refs.md) |

## Consequences

分层机制到位，配置迁移未做——配置不在本仓库内。在配置写上 `tier` 之前，一切行为不变：所有项都在层 0，选点与分层引入前完全一致。迁移应当按资源逐个进行并观察流量分布，一次改完的话，若层划分与原意不符，分布会明显偏移而难以归因。

分层引入一个新的失败模式：某层条件写得过窄会导致该层无节点可用而降级，日志上表现为"降级"而非"配置错误"。指向未定义节点这一类配置错误由[未定义节点引用的校验与摘除](2026-08-27-undefined-flow-server-refs.md)在加载时摘掉并单独报出，不再混进降级信号；条件写得过窄导致的空层仍然只能从降级 warn 上看出来。

`poolize_from_pool` 的参数数到 8，超过 clippy 的阈值，新增一条同类告警（该告警在本仓库已有十余处）。把 `plugin_server_mapping` 与层表合并为"池条目旁挂信息"能消掉它，但两张表用途不同，合并的抽象说服力不足，暂未做。

选点日志多了 `tier=` 一项，解析该日志的工具需要相应调整。
