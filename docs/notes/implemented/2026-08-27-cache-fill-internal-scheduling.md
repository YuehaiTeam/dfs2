# 缓存回填改走内部调度

Status: implemented

## Problem

缓存回填复用发给客户端的那个 URL：为客户端选完点、生成 URL 之后，服务端拿同一个 URL 自己取一遍，把内容写进缓存。这个复用有三处错。

**协议对不上。** URL 会按客户端的传输能力改写方案：`h3_only` 节点给 `http3://`、`dfs_webtransport` 给 `h3wt://`、`dfs_rtc` 给 `wrtc://`。本进程的 fetch 客户端只挂了 H3、SSH、SFTP 三种 middleware，后两种方案根本无法发起。这类回填必然失败，而失败被 `.ok()` 吞掉，既不写缓存也不留痕迹——从外部看就是这个路径的缓存永远不命中。

**方向对不上。** 客户端在国内，选中的是国内节点；服务端在海外，于是回填要绕一趟回国内取，再把内容缓存下来发给所有客户端。选点依据的是客户端的位置，取件却发生在服务端，两者本该各按自己的位置选。

**大小闸门问错了节点。** 是否缓存取决于文件大小，而大小取自健康检查缓存里"某个节点关于某条路径"的记录。用客户端选中的节点去查，得到的是那个节点上的大小，而内容将从另一个方向取来。

## Decision

回填单独调度一次取件，上下文用 `FlowContext::internal()`（见[内部取件的调度上下文](2026-08-27-internal-flow-context.md)），能力面是本进程 fetch 客户端的实际支持面，因此不会选出无法发起的协议。

**回填在为客户端选点之前尝试。** 成功即由缓存供给本次请求，客户端那轮选点从不发生；失败才照常选点并重定向。

**回填供给的记账归回填源节点。** 日流量、分钟流量、调度请求指标都记给 `metadata.src` 指向的节点，那是真实出流量的一方；客户端侧留一条 `cached_download` 日志（`mode=cache`，字节归 `src`），与命中同待遇。Enabled 资源的下载计数与 CDN 记录在该路径上不累计，与命中路径一致——缓存供给不消耗配额，也不产生可惩罚的节点历史。

回填目标是整个文件：`ranges` 置空，与客户端本次请求的区间无关。文件大小沿用请求路径上已探到的全量大小，`size` 类条件因此在内部调度里仍可判定。

大小闸门改问内部调度选中的那个节点——决定"取不取"和决定"从哪取"引用同一个节点。

回填失败不再静默：找不到可用节点、URL 没有节点归属、取件失败，三种情况各留一条 warn。失败不影响本次请求，随后照常为客户端选点并重定向，只是这次没写进缓存。

缓存资格判定（资源开关与前缀子路径匹配）抽成 `cache_eligible`，在选点之前先挡掉不缓存的路径，避免为不会缓存的请求白跑一次内部调度。它同时被 `should_cache_content` 复用，那里原本有一份同样的逻辑。

## Alternatives considered

**继续复用客户端 URL，但在协议无法发起时跳过回填。** 落选：只治协议那一项，取件方向与大小闸门两处仍错。而且"跳过"意味着 H3 类节点服务的客户端永远享受不到缓存，而这些节点往往正是主力。

**回填改为异步任务，不占用本次请求。** 落选（暂）：这会改变响应语义——目前缓存未命中时，首个请求等回填完成并直接拿到内容，改成异步后它只能拿到重定向。变更值得单独评估，与本次的调度方向问题无关。

**让内部调度失败时退回客户端 URL。** 落选：回填内容会分发给此后所有客户端，从一个不该用的节点取到的内容会被放大。宁可不缓存并留下日志。

**把大小闸门改为不依赖健康检查缓存，直接读一次 HEAD。** 落选：多一次往返，而健康检查缓存本就是为这类查询准备的。真正的问题是问错了节点，不是数据来源不对。

**先为客户端选点，回填随后进行。** 落选：回填一成功，客户端那轮选点就只剩记账和日志在生效——字节记给一个实际没出流量的节点，真正供出内容的回填源节点却零记账，`bw_daily`、`server_bw_minutes` 的输入随之失真；那轮选点本身也是白跑。先回填则成功路径只有内部一轮选点，记账自然归位。

## Verification

| 判据 | 结果 |
|---|---|
| 缓存资格只由配置决定，可在选点前判定 | PASS：`cache_eligibility_depends_only_on_configuration` 覆盖普通资源、前缀资源匹配与不匹配、缺子路径、空模式表 |
| 回填不会选出本进程无法发起的协议 | PASS（结构性）：内部上下文的 wt/wrtc 能力为假，能力门据此剔除这两类节点，见 `internal_fetch_can_use_h3_only_servers` 对同一能力面的断言 |
| 回填目标为整个文件 | PASS（结构性）：内部目标的 `ranges` 置空 |
| 大小闸门与取件引用同一节点 | PASS（结构性）：`should_cache_content` 的 `server_id` 取自内部调度结果 |
| 回填失败留痕 | PASS（结构性）：三条失败路径各有 warn，取代原先的 `.ok()` |
| 回填成功时客户端选点不发生 | PASS（结构性）：回填在选点之前尝试，成功即返回，选点代码不可达 |
| 回填供给的流量记给回填源节点 | PASS（结构性）：日流量、分钟流量、调度指标都以 `metadata.src` 为节点记账 |
| 内部调度选到符合服务端位置的节点 | 未实测：需线上观察回填的选点日志，确认落点符合服务端自身的网络位置 |
| 回填路径的端到端行为 | 未覆盖：路由层没有针对回填的自动化测试，验证内部调度真的取回内容需要可控的上游节点 |

## Consequences

回填成功的未命中请求只跑内部一轮选点；回填失败的才两轮都跑（内部一轮加客户端一轮）。选点包含健康检查，因此这是实际延迟而非纯计算——但只发生在缓存未命中且该路径确实要缓存时（缓存命中的请求在更早处就返回了），且 `cache_eligible` 已把不缓存的路径挡在选点之前。

回填成功的请求产生 `cached_download` 日志与归于回填源节点的流量，没有 `direct_download` 日志，也没有客户端侧的每节点流量记账。分析侧按 `mode=cache` 剔除或单算即可，但假定"每次未命中都有一条 direct_download"的统计在这类请求上会看到缺口。

H3 类节点服务的客户端第一次能享受到这些路径的缓存。此前它们的回填一直在静默失败。

回填的供出节点与客户端的下载节点从此可能不同。缓存条目已经记录供出节点（见[缓存条目记录供出节点](2026-08-27-cache-provenance.md)），响应头 `x-dfs-cache-from` 因此会出现与客户端本次选点不同的节点名——这是正确的，它回答的是"这份缓存内容来自哪里"。
