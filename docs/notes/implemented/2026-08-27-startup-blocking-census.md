# 启动被版本文件普查阻塞

Status: implemented

## Problem

进程完成容器初始化后，先同步跑完一整轮版本文件普查，才开始监听端口。某次线上重启的日志显示，从容器初始化完成到 HTTP 开始监听相隔 60.6 秒（单实例，配置中有一个资源带数条版本文件路径，其中一个节点的 H3 端点当时不可达）。这段时间里进程既不接受下载请求，也不响应 `/metrics` 与健康检查，从外部看等同于停机。

时间几乎全部花在对不可达节点的重复等待上。H3 连接超时是 10 秒，而普查按版本文件路径逐条探测，同一个不可达节点在同一轮普查里被每条路径各探一次，每次都付满 10 秒——该轮日志中出现三次同一节点的 H3 连接超时。

跳过不可达节点的机制其实已经存在：`census_all` 与 `census_resource` 都接受 `skip_server_ids`，`dfs2 validate` 在普查前并发 ping 所有配了健康检查路径的节点，把失败的节点作为跳过集合传进去。服务器启动路径没有接这一步，传的是空集合。

并发度也没有用在最耗时的维度上：`collect_observations` 在单条路径内对多个节点并发探测，但路径与资源两层都是顺序循环，路径数多时并发只作用在最内层。

一个资源下某条版本文件路径无任何节点响应时，运行时完全静默：`report_view` 只在 `strict_split_fail` 为真（`dfs2 validate` 路径）时才输出 no-live-responders，普查的后台轮次连日志行都没有。

## Decision

**首轮普查由后台任务承担。** `start_background_task` 用的 `tokio::time::interval` 首个 tick 立即触发，因此启动路径不再另跑一次普查——那与后台首轮是同一件事做两遍。普查结论缺失不影响对外服务：`evaluate_path` 此时返回 `VersionFileDecision::Unknown`，而 `is_server_healthy` 里 `Match | Unknown` 是直通分支，请求退回普通健康检查；`VersionFileView` 在数据存储中的 TTL 是 86400 秒，重启后上一轮结论仍可用，首轮并非从零开始。

**每轮普查前先实测连通性。** `ping_servers` 并发 ping 所有配了健康检查路径的节点，返回 `PingReport`；`ping_and_census_all` 取其 `unreachable()` 作为 `skip_server_ids`。ping 按节点数付一次超时，取代原先按节点数乘路径数重复发现同一个节点不可达。`dfs2 validate` 改用同一个函数，因此它认定的失败节点集合与运行时普查跳过的集合出自同一份代码。

`ping_servers` 不读健康信息缓存：这个结果决定普查是否整轮跳过某节点，而过期的"不可达"判定会让该节点缺席一整轮多数派计算，节点数少时足以改变多数派是否成立。

**资源层与路径层并发。** 同一资源下的多条版本文件路径、以及多个资源都并发普查，路径之间无共享状态，汇总由资源层做。探测并发由 `VersionFileService` 持有的服务级信号量约束，容量为 `PROBE_CONCURRENCY`；信号量若按路径新建，实际在飞探测数会变成 `PROBE_CONCURRENCY` 乘以并发路径数。

**单次版本文件探测有 15 秒总时限。** 底层客户端的分段超时之和（H3 连接 10 秒、HTTP 读 60 秒）远大于取一个版本文件该花的时间，总时限使单轮普查的最坏耗时有明确上界。

**一条路径的 view 存储失败不再中断同资源的其它路径**，而是记入该路径的报告。

**`dfs_version_file_no_responders{resource_id}` 上报该资源下无任何节点响应的版本文件数。** 它与 `dfs_version_file_no_majority` 互斥：无响应者时 `split_since` 是从上一轮继承的，不代表本轮观测到分歧，因此这类路径只计入 no_responders。运行时不为这种情况输出日志，该指标是它在监控侧唯一的出口。

**IP 地理库在启动时用 `spawn_blocking` 预热**，不再由第一个到达的请求承担整个数据库的读取。

## Alternatives considered

**保持普查阻塞监听。** 其原意是不在版本文件状态未知时对外服务。落选：普查结论只影响版本文件读取，而该路径有 `Unknown` 直通的回退；用它阻塞整个 HTTP 面会一并挡住下载、指标与健康检查这些与版本文件无关的接口。

**缩短 H3 连接超时。** 落选：10 秒是为真实可用但握手慢的 H3 路径留的余量，调小会误判正常节点。问题在于重复付这个超时，不在它的取值。

**普查跳过 H3 节点。** 落选：这些是真实的服务节点，它们的版本文件正是需要普查的对象。

**把节点不可达状态跨轮缓存。** 落选：会让恢复的节点在一段时间内继续被跳过，把普查结论钉在过期状态上。

**轮内补记探测阶段新发现的不可达节点。** 指 ping 通过、但版本文件路径探测连接失败的节点，在本轮剩余路径中并入跳过集合。落选，三个理由叠加：路径并发后同一节点的多次超时是重叠而非串行，单轮耗时不再随路径数增长；实现它需要先区分"连接失败"与"服务器回了非成功状态"，而 `execute_full_probe` 对两者都返回 `is_alive: false`，加这个区分只为一个消费者不划算；跳过集合在并发路径间共享会让观测结果依赖调度时序，同一节点可能在一条路径上有观测、在另一条路径上被跳过，多数派计算失去可解释性。15 秒总时限已为这种节点的代价设了上界。

**让 ping 读健康信息缓存以进一步加速。** 落选：见上文不读缓存的理由，一次过期的"不可达"判定的代价是该节点缺席整轮多数派。

## Verification

| 判据 | 结果 |
|---|---|
| 首轮普查不阻塞监听 | PASS：启动路径不再 await 普查，首轮由后台任务的立即 tick 承担 |
| 普查未完成期间版本文件请求不失败 | PASS：`is_server_healthy` 的 `Match \| Unknown` 直通分支；`VersionFileView` TTL 86400 秒使重启后仍有上一轮结论 |
| 单轮普查耗时有上界 | PASS：上界为单次探测 15 秒乘以 ⌈节点数×路径数 / `PROBE_CONCURRENCY`⌉，不再随路径数线性叠加超时 |
| 一个不可达节点最多付一次连接超时 | 部分达成：ping 阶段每节点一次；ping 通过而版本文件路径探测超时的节点仍按路径各付一次，代价由路径并发与 15 秒总时限共同封顶 |
| 无响应者可观测 | PASS：`silent_cluster_is_not_reported_as_a_split`、`no_responders_only_surfaces_in_strict_mode` 钉住了分类与运行时静默 |
| validate 与运行时使用同一套探测 | PASS：两者都经 `ping_servers`；`unreachable_lists_only_failed_pings`、`servers_without_implementation_are_not_reported_unreachable`、`servers_without_health_check_path_are_not_probed` |
| 节点全部不可达时进程仍在秒级完成监听 | 未实测：需在线上重启后比对进程启动与 `Starting HTTP server` 的时间差 |
| 首个请求不含地理库加载 | 未实测：预热是 `spawn_blocking`，与第一个请求存在竞争，只保证不再串行等待，不保证一定先完成 |

## Consequences

启动时间与节点可达性解耦：普查慢不再表现为服务不可用，而是表现为普查结论在启动初期尚未刷新，此期间版本文件读取走普通健康检查。这把一个停机问题换成了一个数据新鲜度问题。

普查一轮的耗时从"节点数乘路径数乘单次超时"降为"总探测数除以并发度乘单次超时上界"，并且 `PROBE_CONCURRENCY` 现在真正约束全局在飞探测数。代价是重启瞬间对节点的并发压力比原来集中，节点数与最小带宽变化时这个上限需要重新审视。

已知缺口两处。ping 通过而版本文件路径不可达的节点仍会在每条路径上各付一次探测，最坏 15 秒，只是这些等待现在互相重叠。地理库预热与首个请求之间没有同步，冷启动后立刻到达的请求仍可能撞上加载。
