# 加权随机选点的区间边界

Status: implemented

## Problem

`weighted_random_selection` 从半开区间 `[0, total_weight)` 抽样，却用闭比较 `random_weight <= *weight` 判定命中。每个条目因此多占一格，两个后果。

等权时末位不可达。权重 `(1, 1)` 的池子总权重为 2，抽样只会得到 0 或 1，而首位在两种取值下都命中（`0 <= 1` 与 `1 <= 1`），第二个节点永远选不到。实测 400 次抽样中它一次都没出现。权重 `(5, 5)` 的实际配比是 6:4 而非 5:5。偏差随权重减小而放大，恰好落在权重从三位数降为个位数之后最要紧的区间上。

首位 0 权重的条目会被选中。配置里用 `server <id> 0` 表达"这类客户端不要用这个节点"，而抽样得到 0 时首位条目命中，概率为 `1/total_weight`。也就是说该条目表达的禁用意图被反转成了小概率启用。0 权重条目位于首位之外时不受影响——前一个条目的闭比较把对应的抽样值吃掉了——所以这个缺陷只在特定排列下显形，也因此长期没有暴露。

## Decision

比较改为严格小于，与半开抽样区间对齐。权重从此表达单一含义：条目被选中的相对份额，0 表示不参与选点。

## Alternatives considered

**把抽样区间改成闭区间 `[0, total_weight]`。** 落选：这会让抽样值多出一个取值，末位条目的份额比权重多一格，问题只是从首位挪到末位。

**保留闭比较，改为在入池时过滤掉 0 权重条目。** 落选：只治 0 权重那一半，等权配比偏斜依旧。且入池过滤会让"0 表示禁用"变成一条隐式规则，而在选点层它本来就能自然成立。

**用现成的加权抽样库（如 `rand` 的 `WeightedIndex`）。** 落选：池子在选点过程中会因健康检查失败被就地移除后递归重选，分布结构每轮都变，预构建的别名表用不上，收益抵不上引入的抽象。

## Verification

| 判据 | 结果 |
|---|---|
| 等权两节点的末位可被选中 | PASS：`weighted_selection_respects_exact_weights`；把比较改回 `<=` 时该断言失败（400 次抽样中末位零次） |
| 等权时长程配比接近均分 | PASS：同一测试断言首位占比落在 40%–60% |
| 首位 0 权重条目不被选中 | PASS：同一测试对 `(0, 1, 1)` 排列做 400 次抽样，0 权重条目零次命中 |
| 既有权重分布与 0 权重行为不回退 | PASS：`test_weighted_random_selection` |

## Consequences

配置中各条目的实际流量份额从此与写下的权重一致。已有的权重配比会随之轻微改变——原先靠前的条目多占的那一格没有了，条目越多、权重越小，改变越明显。这是把实际行为对齐到配置意图，而不是引入新的偏好。

`server <id> 0` 现在确实表示禁用。配置中依赖这一语义的条目（按客户端归属地把某节点权重置零）从此按预期生效；此前它们在特定排列下有 `1/total_weight` 的概率被选中。

池子内全部条目权重为 0 时仍然报错而非静默选点，该行为未变。
